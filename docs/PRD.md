## 一、问题陈述

**谁**：创意从业者——内容运营者、游戏/交互设计学生与从业者。他们每天依赖 3-7 个专业软件（Figma、Blender、Premiere、Notion、Unity、Photoshop、Excel 等），并已大量接触生成式 AI 工具。

**什么场景**：2024-2026 年间，AI 把"写一个 Photoshop 脚本""生成一版海报初稿""剪一条口播"这些原本需要专业软件才能完成的事，压到了对话里完成。他们隐约感到自己某个常用软件"快没用了"，但说不清是哪一个、为什么。

**现在怎么解决**：去搜"AI 会不会取代 XX"。搜到的结果分两类，都不行：
1. **职业层测评**（"AI 会不会取代设计师"）——分析单位是职业（occupation），而同一个岗位里不同人的工具组合天差地别，结论不可迁移到"我这个软件"。
2. **分析师榜单**（"189 个 SaaS 品类被 AI 替代指数"）——分析单位是软件品类，但分数是分析师在办公室里打的，不含使用者侧数据，用户只能读不能测，也不解释"为什么是这个分"。

**为什么不行**：因为真正决定"我会不会弃用这个软件"的，不是这个软件的功能有多容易被 AI 复刻，而是**我在这个软件里到底存了多少"带不走的自己"**。这个量，只有使用者本人知道，任何二手数据都测不到。

**本产品要解决的问题**：给创意从业者一个 30 秒的、可解释的、分析单位是「我 × 我的某个具体软件」的自测工具；同时把每一次自测变成一条匿名结构化数据，用于回答一个还没有人系统回答过的研究问题。

## 二、目标用户

### 主画像 A：焦虑的自省者（第一批种子，占比预计 55%）

| 项 | 内容 |
|---|---|
| 年龄/身份 | 22-32 岁，游戏/交互设计从业者或在读研究生 |
| 技术水平 | 高。能熟练使用 3 个以上专业软件，已用过 Midjourney / Cursor / Claude 等至少 2 个 AI 工具 |
| 触发场景 | 刷到"AI 取代 XX"的内容后 3 分钟内；或在工作中第 N 次用 AI 绕开了某个原本要开软件的操作后 |
| 花 30 秒的动机 | **不是要建议，是要一个外部验证**。他心里已有判断，来求证 |
| 看到结果第一反应 | **对比**。不是看自己的分，是先在脑子里把它和另一个软件比："它居然说我的 Notion 比我的 Figma 更安全？" |
| 会不会分享 | 会，但**只分享反直觉的结果**。符合预期的结果不分享（没有信息量），违背预期的结果立刻截图 |

> 设计推论：结果页必须制造"反直觉感"。分享文案必须是第一人称断言句（"我常用的 XX 被判定为高危区"），不是工具介绍。

### 主画像 B：同温层围观者（传播引擎，占比预计 30%）

| 项 | 内容 |
|---|---|
| 身份 | 小黑盒 / 知乎 / 即刻 / 小红书的内容消费者兼创作者 |
| 行为 | 不是来测自己的，是来**找素材**的。会连测 5-10 个软件，横评截图发圈 |
| 关键需求 | 结果卡片必须**可单独截图**、**不刷新就能再测一个**、**不强制注册** |

> 设计推论：轮询成本要低。测完一个后必须有显眼的"再测一个"入口，且不清空上下文。

### 次画像 C：工作坊参与者（研究资产，占比预计 15%）

| 项 | 内容 |
|---|---|
| 身份 | 后续 co-design 工作坊的受邀对象（设计/媒体专业学生与从业者） |
| 行为 | 带着"我要帮同学改进这个工具"的心态来，会认真写反馈、会挑刺 |
| 关键需求 | 一个显眼的"这个结果准不准"反驳入口 |

> 设计推论：**反驳数据本身就是质性研究素材**。这个入口既是 UX 需要，也是论文里"参与者对量表构念的反驳与修正"一节的原始材料，成本极低而学术价值极高，必须做。

### 第一批种子从哪来
1. 洪兄本人的小黑盒 / 知乎账号（已有真实内容账号运营经验，冷启动成本最低）
2. 澳门科技大学人文艺术学院同学（同温层，且是工作坊的现成招募池）
3. 设计/游戏类社群（需控制单一社群占比不超过 30%，避免样本同质性过高被评审质疑）

## 三、竞品分析

### 3.1 直接竞品（AI 替代风险自测类，5 项）

| 名称 | 形态 | 核心机制 | 明显缺陷 |
|---|---|---|---|
| **job-risk.com** | Web 交互式测评（2 分钟 / 8 题快速版） | 从 ESCO 3,039 个职业库选职业 → 算法 = Tufts 大学 757 职业 AI 暴露度（权重 55%）+ 个人任务自评（25%）+ 情境因素（20%） | 权重致命：**55% 来自职业层统计数据，你自己的回答只占 25%**。两个用完全不同工具的设计师，只要职业名相同，分数就高度趋同。这恰恰是 Frey & Osborne 被批评的那个错误——用职业均值掩盖任务组合差异 |
| **careery.pro「Will AI Replace Me?」** | Web 极简 4 题测（<2 分钟） | AI Resistance Score 四维各 0-25 分：身体在场 / 人际关系 / 创造性判断 / 伦理问责 | 维度是**职业层面的人格化属性**（你是不是要在现场、要不要共情），完全不适用于"某个软件"这个分析单位。一个软件不"在场"也不"共情"，量表直接失效 |
| **ThePivotWave AI Readiness Assessment** | Web 30 题 5 维（约 10 分钟） | 五维等权平均：颠覆暴露度 / 当前 AI 技能 / 适应力 / 职业流动性 / 战略意图 | **把两个不同构念混进一个分数**：第 2、3 维（AI 技能、适应力）是 TAM/UTAUT 的"采纳度"问题，第 1 维（暴露度）是"任务结构"问题。采纳度高就给你降风险分，但一个人可以既很会用 AI、又工作在被高度自动化的任务上。构念效度为零。30 题也远超"30 秒"心理阈值 |
| **solidaitech AI Job Risk Calculator** | Web 3 步表单 | 三数据点启发式：任务类型 + 工作环境（全屏/混合/线下）+ 当前 AI 使用度 | 最露骨的营销化设计：**"AI Mitigator" 因子——只要你勾选"我积极用 AI"，脆弱度分就大幅下降**。这不是测量，是说服。免责声明自己也承认"algorithmic approximation" |
| **keencalc AI Job Replacement Risk Calculator** | Web 4 因子滑块 | 职业基线 + 常规任务占比 + 身体在场 + 专业资历，明确引 Frey & Osborne (2013) 与 Eloundou et al. (2023) | 值得尊敬的诚实——页面自己写明"这些 baseline 是本社编辑打分（editorial points），不是人口估计值，不是从论文里取的数"。但正因如此，它**自认为不可用作研究工具**。且滑块的"−25 分"这类调整量没有任何校准依据 |

### 3.2 最接近的相邻品（软件级，1 项）

| 名称 | 形态 | 核心机制 | 明显缺陷 |
|---|---|---|---|
| **WhatAreTheBest · Agent Replacement Index** | 静态研究报告（非交互） | 给 189 个 SaaS 品类打 0-10 分。脆弱侧 5 因子：工作流依赖 / 界面复杂度 / 手动任务频次 / 数据可迁移性 / 集成商品化。防御侧 5 因子：系统记录地位（system-of-record）/ 专有数据护城河 / 网络效应 / 合规要求 / 物理嵌入 | **这是全网唯一以"软件"为分析单位的 AI 替代评估，也是本项目最需要正面对话的对象**。但缺陷明确：(1) 打分由该司研究团队人工完成，无用户侧数据；(2) 用户只能读不能测；(3) 分数以品类为单位，"你用的 Figma"和"Figma 这个品类"是两回事；(4) "数据可迁移性"只被当作脆弱因子，没意识到它与"状态沉淀"是乘积关系而非加减关系 |

### 3.3 替代方案（用户当前的土办法，2 项）

| 名称 | 形态 | 核心机制 | 明显缺陷 |
|---|---|---|---|
| **SaaS Replacement & Tool Audit（claudeforoperators.com）** | Prompt 模板 + 清单流程 | 让 Claude 帮你盘工具清单 → 每个工具打 1-5 分可替代性 → 算真实成本（订阅费 + 迁移工时 + 培训 +  disruption） | 优势是**算经济账**（这点本项目不做，也不该做）。缺陷：评估由 LLM 生成，同一工具两次跑可能给不同分；无跨用户可比性；**零数据采集能力**，无法支撑任何量化分析 |
| **雪球《AI替代软件可能性评估》** | 投资视角的五维分析框架 | 业务逻辑抽象度与容错率 / 网络效应与转换成本 / 物理世界交互 / 数据专有性与闭环 / 法规合规 | 作者自称"仅供参考，不作为投资建议"。分析单位是**公司商业模式**而非"你用的工具"。其中"容错率"一维与本项目高度相关，是本项目"结果确定性与容错率"题的直接民间来源，可引为行业实践佐证 |

### 3.4 竞品最大空白点（一句话）

> **全网没有任何一个交互式自测工具，把分析单位放在「使用者 × 他自己的某个具体软件」这一层。**职业层测评（job-risk.com / careery）测不到软件差异；软件层榜单（Agent Replacement Index）测不到使用者差异。这个交叉层是空的。

**次空白点（三条）**：
1. **分数不可解释**：所有工具都只给总分和维度分，没有一款告诉你"是哪一道题把你推到高危区的"。逐题可解释是本项目最低成本、最高感知的差异点。
2. **把"AI 采纳度"当减分项**：几乎所有工具都这样。这是混淆两个构念（采纳行为 vs 任务结构），是本产品方法论章节可以直接引用的批评靶子。
3. **无纵向设计**：没有一款工具回访问过用户"你后来真的换了吗"。自评量表无法自我验证预测效度，这是整个品类的共同软肋，也是本产品可以用极低成本补上的一环（见第六节 R6）。

### 3.5 我们的差异化

| 维度 | 竞品 | 我们 |
|---|---|---|
| 分析单位 | 职业 / 岗位 / SaaS 品类 | **使用者 × 具体软件** |
| 数据来源 | 分析师打分 / 职业统计库 | **使用者自评，逐题留痕** |
| 可解释性 | 总分 + 维度分 | **逐题回溯：哪道题把你推进了高危区** |
| 采集能力 | 无（多数明说"数据不存储"） | **每次自测 = 一条匿名结构化数据，目标是 200+ 样本** |
| 理论出处 | 引 Frey & Osborne 但不交代如何操作化 | **每题标注对应理论与文献，可被评审逐条追问** |
| 身份 | 营销获客工具 / 内容页 | **学位作品 + 论文数据采集装置**，利益关系声明前置 |

## 四、学术理论锚点（核心章节）

> **红线声明**：以下每一条都标注核实状态。「已核实」= 本轮联网检索到一手 PDF、出版社页面或权威二手来源（OECD 报告、DBLP 等），且作者/年份/题名三项一致。「待核实」= 未检索到一手来源，或卷期页码/作者全表未能确认。**凡标"待核实"的，洪兄必须在 Web of Science / Google Scholar / 知网复核后才可写进论文。宁可少引，不可引错。**

### 锚点 1（主锚点）：任务可自动化模型及其批评

| 项 | 内容 |
|---|---|
| 核心主张 | 自动化的分析单位应是**任务**而非职业。Frey & Osborne 请 AI 研究者对 70 个 O*NET 职业做"可否完全自动化"标注，再用 9 个 O*NET 变量（原创性、手指灵巧度、谈判、说服力等）代理三大工程瓶颈（感知与操纵、创造性智能、社会智能），外推到 702 个职业，得出美国 47% 就业处于风险中 |
| 与状态承载量的关系 | **本项目是这条线索的下移**：Frey & Osborne 的分析单位是 occupation，本项目下移到「软件 × 使用者沉淀的状态」，分析单位比 task 更细一层。这直接回应了学界对该模型最集中的批评 |

### 锚点 2（主锚点）：工具中介与工具生成（Instrumental Genesis）

| 项 | 内容 |
|---|---|
| 核心主张 | 源自维果茨基/列昂节夫的活动理论。核心区分是 **artifact（人工物，纯物质/功能侧） vs instrument（人工物 + 使用者在其上长出来的"使用图式" utilisation schemes）**。**同一件 artifact 在不同使用者手里会生成完全不同的 instrument。**生成过程叫"工具生成"（instrumental genesis），含两个子过程：面向主体的 *instrumentation*（使用者心理图式的生成与演化）与面向人工物的 *instrumentalization*（使用者给人工物赋予新功能、改造它） |
| 与状态承载量的关系 | **这是「状态承载量」最直接、最硬的理论落点，也是用户初稿第四维（学习成本形态）的理论根据。**<br>AI 能复制的是 **artifact**（功能清单、菜单位置、操作路径——这些可被自然语言压平）；AI 复制不了的是 **instrument**（使用者在这个 artifact 上长出来的判断力、路径依赖、肌肉记忆）。<br>所以可以下一个干净的定义：**状态承载量 ≈ instrument 相对于 artifact 的超出部分。**这句话可以直接进论文的构念定义段 |

### 锚点 3（主锚点）：分布式认知与认知人工物

| 项 | 内容 |
|---|---|
| 核心主张 | 认知过程不局限于个体颅骨内，而是分布于**人、人工物、环境、以及时间**之中。Hollan/Hutchins/Kirsh 明确提出三种分布：跨社会群体成员分布；内部结构与外部（物质/环境）结构之间的协调分布；**沿时间分布——早期事件的产物会改变后期事件的性质** |
| 与状态承载量的关系 | 第三种分布（沿时间分布）就是「状态沉淀」的严格理论表述。软件里存的不是数据，是**被冻结在外部介质上的早期认知产物**，它决定了后续所有工作的起点与成本。Norman 的"认知人工物"则给出了最简洁的定义句：**"维持、显示或操作信息以服务于表征功能、并影响人类认知表现的人工装置"**——这句话可以直接作为论文里"软件作为认知人工物"的引出句 |

### 锚点 4：任务—技术匹配（TTF）

| 项 | 内容 |
|---|---|
| 核心主张 | 技术功能、任务需求、个体能力三者的**匹配度**决定使用与绩效。Goodhue & Thompson 提出时明确针对 TAM/TRA/TPB 的缺陷：**采纳 ≠ 绩效**，使用率不能预测个人绩效，只有匹配才能 |
| 与状态承载量的关系 | 提供"为什么高承载工具难以替换"的机理解释：当匹配度高到**任务反过来迁就技术**（学界称为 unilateral dependence，任务向技术单向依赖），替换技术就等于重写任务。这是"状态承载"产生替代阻力的因果链条中缺失的一环。<br>同时 TTF 也是批评竞品的武器：把"你用不用 AI"（TAM/UTAUT 的采纳问题）和"你的工作是否可被自动化"（任务结构问题）混进一个分数，正是 Goodhue & Thompson 1995 年就批评过的错误 |

### 锚点 5：责任归属与道德缓冲区（用户初稿第三维的直接落点）

| 项 | 内容 |
|---|---|
| 核心主张 | 在人机系统中，控制权被分布到多个行动者，而社会与法律的问责仍然指向个体。结果是人成为 **"道德缓冲区"（moral crumple zone）**：就像汽车的溃缩区吸收撞击力，高度自动化系统中的人会（偶然或有意地）承担系统失效的道德与法律责任。**汽车的溃缩区保护人，道德的溃缩区保护技术系统的完整性，代价由最近的人类操作员承担** |
| 与状态承载量的关系 | 责任越不可外包，AI 越难整包接管——这是一个**制度性**替代壁垒，与工具的功能强弱无关。这是本项目唯一一个竞品完全没有的维度（careery 的"伦理问责"只覆盖医疗/法律/航空，不覆盖创意工作者的"声誉兜底"）。<br>**但必须点出双重性**：责任不可外包，意味着人在这件事上被"钉"住了，这既是保护（不会被替代）也是负担（成为缓冲区）。论文里把这个双重性写出来，比只写保护面更经得起追问 |
| 文献线索 | Elish, M. C. (2019). Moral crumple zones: Cautionary tales in human-robot interaction. *Engaging Science, Technology, and Society*, 5, 40–60. —— **已核实**（DOAJ 收录 + 作者机构 EPIC 页面，另有 2016 年 WeRobot 会议版，SSRN DOI 10.2139/ssrn.2757236） |

## 五、对「状态承载量」定义的验证与修正

### 5.1 对初稿假设的逐条判断

初稿假设：「工具的保留意愿与其状态承载量正相关，与任务一次性程度负相关。」

| 假设 | 判断 | 理由 |
|---|---|---|
| 与状态承载量正相关 | **部分同意，但不完整** | 缺了调节项：只"承载"不够，还要"带不走"和"重建不了"。Obsidian + Markdown 承载量极高（我全部笔记都在里面），但因为可迁移、可由 AI 一次性重建（纯文本），实际替代风险**高**。反例成立 → 假设需修正 |
| 与任务一次性程度负相关 | **同意，且是最扎实的一条** | 直接对应 Frey & Osborne 的核心（可编码的常规任务最先被自动化），也是四个假设里唯一有成熟实证传统的一条 |

### 5.2 建议修正后的定义（可直接进论文）

> **状态承载量（State-Carrying Capacity, SCC）**：在一个特定使用者的工作流中，某软件所承载的、无法在合理成本内迁移或重建的状态总量。
>
> 状态包含三类：
> 1. **数据状态**——文件、历史版本、素材库、项目上下文
> 2. **工具状态**——配置、插件、模板、工作流编排
> 3. **使用者状态**——使用图式、判断力、肌肉记忆（对应 Rabardel 的 *utilisation schemes*，即 instrument 超出 artifact 的部分）
>
> **替代阻力 ≈ 状态承载量 × 状态不可迁移性 × 状态不可重建性**
>
> 三项为乘积而非加和：任一项趋近于零，替代阻力即趋近于零。这解释了为什么"承载量大"的软件仍然高危（Markdown 笔记库），也解释了为什么"承载量不大"的软件可能安全（一个只有 3 个文件、但甲方必须在里面评审的协作画板）。

### 5.3 必须写进论文的一句免责（护身符）

> 本研究测量的是**使用者感知的状态承载量（perceived SCC）**，而非客观的替代概率。感知与真实替代行为之间的一致性，需通过纵向回访检验（见 R6）。

这句话不写，评审可以一枪打死"你怎么证明你的分数是对的"。写了，研究性质就变成"探索性量表开发 + 感知测量"，方法论上完全站得住。

## 六、8 题维度的专业建议

### 6.1 对初稿四维度的批判意见

| 初稿维度 | 判断 | 问题与处置 |
|---|---|---|
| **状态沉淀**（关掉它，你的积累还在不在） | 保留，最强的一条 | **但混了两个变量。**"积累还在不在"问的是沉淀量；"我能不能把它带走"问的是可迁移性。这两个变量对结论的作用**相反**，必须拆成两题（A1 沉淀 / A2 可迁移性，反向）。这是初稿最大的方法论问题 |
| **可回滚性**（生成错了能不能退回） | **建议整条替换** | 见锚点 6。这是**规范性设计准则，不是预测变量**；且方向可能反了（可回滚性高 → 试错成本低 → AI 更容易介入）。替换为 **B3「结果确定性与容错率」**：错了代价多大 / 对不对能不能客观验证 |
| **责任归属**（出错了 AI 能替你负责吗） | 保留，最有差异化 | 但要落地：创意从业者的"责任"通常是**声誉与客户关系**，不是法律责任。题面必须用"兜底""后果"这类他们真能感知的词，不要用"法律责任" |
| **学习成本形态**（记菜单位置 vs 建立判断力） | 保留，最有理论味 | **但它是一道分类题，不是程度题。**硬塞进 Likert 求和会污染总分。处置：改为**不计分的分层变量 S1**，用作**调节变量**去检验"同样是高危分，'记菜单型'用户后来真的换了吗，'判断力型'没有吗"——这个假设如果能验证，是本项目最漂亮的一节 |

### 6.2 初稿遗漏的维度（建议补两条）

1. **协作锁定 / 网络效应（C2）**：初稿完全从"我一个人 vs 工具"出发，漏了"别人也在用"这一层。但创意从业者最硬的壁垒往往在这里——甲方要在 Figma 里评审、交付格式就是 .psd、团队历史版本在 Notion 里。AI 无法单方面迁移他人。竞品 Agent Replacement Index 把 network effects 列为防御侧因子，本项目必须覆盖。
2. **中间态 vs 终态（B2）**：端到端生成冲击的是"产出了就交付"的环节。如果你用工具产出的东西还要被继续加工，替代它就等于重构整条链，成本陡增。这一条把 Frey & Osborne 的"任务"视角拉到了"工作流链条位置"上。

### 6.3 计分题（8 题，5 点 Likert，3 因子）

计分口径：1 = 完全不符合，2 = 不太符合，3 = 说不清，4 = 比较符合，5 = 完全符合。**总分范围 8-40**（反向题已反转后求和）。

**因子 A｜状态承载（3 题）** —— 理论落点：Rabardel 工具生成 + 分布式认知 + 转换成本

| # | 题面 | 测什么 | 为什么这条能预测 | 方向 |
|---|---|---|---|---|
| A1 | 这个软件里，存着我换一个工具就带不走的东西——历史版本、素材库、我调好的配置、这个项目的来龙去脉 | 数据与工具状态的沉淀量 | 沉淀越多，AI 要替代的不只是"功能"，而是"把你的过去一起搬走"。这正是 SCC 定义里的第一类与第二类状态 | 正向 |
| A2 | 我放在这个软件里的东西，可以完整地导出成别的地方也能打开、也能用的格式 | 状态可迁移性 | **反向题，A1 的调节项。**解释了为什么"承载量大"不等于安全——Obsidian 里 3000 篇 Markdown 承载量极大，但纯文本可被 AI 一次性重建 | **反向** |
| A3 | 我每多用这个软件一年，下一次开工就更省事一点 | 状态是否随时间复利 | 区分"活资产"与"死资产"。不随时间复利的积累是一次性投入，AI 重建它只需一次；随时间复利的积累（快捷键、判断力、素材库的语义结构）重建成本随时间增长 | 正向 |

**因子 B｜任务结构与确定性（3 题）** —— 理论落点：Frey & Osborne 任务模型 + 容错率

| # | 题面 | 测什么 | 为什么这条能预测 | 方向 |
|---|---|---|---|---|
| B1 | 我用它做的事，基本都有固定套路，每次差别不大 | 任务一次性程度 / 常规化程度 | 初稿假设里最扎实的一条，也是 Frey & Osborne 的核心机制：可编码的常规任务最先被自动化 | **反向** |
| B2 | 我用它产出的东西，大多数时候还要被我或别人继续加工，很少直接作为最终交付 | 中间态 vs 终态 | 端到端生成冲击的是"产出即交付"。若产出只是链条中间态，替代它等于重构整条工作流，替代成本陡增 | 正向 |
| B3 | 它输出的结果对不对，我能立刻客观地判断出来，而且错了代价也不大 | 结果确定性 / 容错率 | **替换初稿"可回滚性"**。生成式 AI 是概率模型，高容错率环节最先被渗透；要求 100% 确定性的环节（合规、精修像素、清算）存在结构性壁垒。<br>另有一层反向机制：结果可客观验证 → 人可以退居质检者 → 反而更容易被替代。这一双重性建议在论文中说明 | **反向** |

**因子 C｜制度与协作嵌入（2 题）** —— 理论落点：Elish 道德缓冲区 + 网络效应

| # | 题面 | 测什么 | 为什么这条能预测 | 方向 |
|---|---|---|---|---|
| C1 | 用它产出的东西出了问题，最后要我来兜底，而且这个后果没法转嫁给工具方或供应商 | 责任归属 / 问责不可外包性 | 责任越不可外包，AI 越难整包接管。这是制度性壁垒，与工具功能强弱无关。**注意双重性**：这也是"道德缓冲区"——人被钉住既是保护也是负担，论文里要写明 | 正向 |
| C2 | 我用它，很大程度上是因为别人（同事、客户、协作方）也在这里，或者交付格式就要求在这里 | 协作锁定 / 网络效应 | **补初稿之漏。**AI 无法单方面迁移他人。甲方要在 Figma 里评审，这个壁垒与 Figma 的功能好不好、AI 能不能画界面完全无关 | 正向 |

### 6.4 分层 / 调节题（不计入总分，3 + 1 可选）

| # | 题面 | 类型 | 作用 |
|---|---|---|---|
| S1 | 你在这个软件上花的学习成本，主要是哪一种？<br>A 主要花在记住东西在哪、怎么操作<br>B 一半一半<br>C 主要花在练出判断力（知道什么叫好、什么该改） | 三档强制单选 | **对应 Rabardel 的 artifact vs instrument 之分。**A 类成本可被 AI 用自然语言压平；C 类成本压不平。<br>**作为调节变量使用**：检验"同为高危分，A 类用户 6 个月后真的换了吗，C 类没有吗"。这是本项目最有可能做出原创发现的一节 |
| S2 | 你用这个软件多久了？ | 分档单选 | 锚定题。用于剔除"用了三天就来打分"的噪声样本，也用于检验 A3（时间复利）的组间差异 |
| S3 | 你平均每周用它多少次？ | 分档单选 | 锚定题。与 S2 一起构成使用强度，用于效度校验（使用强度应与 A 因子得分正相关——若不相关，量表本身有问题） |
| S4（可选） | 这个软件是你自己选的，还是公司 / 客户 / 课程要求的？ | 二选一 | 被动使用者在 C2 上会系统性高分。用于后续分析时做分层，避免把"被锁定"误读为"安全" |

### 6.5 关于计分档位的两条硬建议

**（1）不要用 0-1-2 三档，用 5 点 Likert。**
三点序数计分会严重压缩方差，且不满足因子分析对连续变量的假设。文献依据：系数 α 随量表点数增加而上升，到 5 点后趋于平缓（Lissitz & Green, 1975；**出处卷期待核实**）。**用户担心"5 点会让 30 秒变 60 秒"是错的**——5 个点选和 3 个点选的操作耗时差异在 1 秒以内，但换来的是方差、α 与因子分析的可行性。

**（2）档位切点上线时不要写死。**
MVP 阶段用**相对分位**展示（≤P33 高危区 / P33-P67 观察区 / >P67 安全区），后台同时存原始总分。等 N ≥ 150 后用 k-means（k=3）校准绝对切点，并在论文里单列一节"切点校准"。
理由：上线前拍死切点，就是洪兄自己最反感的"拍脑袋"；而"用数据校准切点"这个动作本身，就是论文里能加分的方法论自觉。

### 6.6 8 题够不够做出有统计意义的结论？

**结论：8 题不够做"有统计意义的因果结论"，但 8 题够做"合格的探索性量表开发与数据采集"——前提是做对三件事。**

| 评估项 | 判断 | 依据 |
|---|---|---|
| 8 题测 8 个维度（一题一维） | **不可行** | 单题无法计算 Cronbach's α，无法做探索性因子分析（EFA），无法验证构念效度。量表开发文献明确要求**每个因子至少 3-4 题**（Hinkin, 1998），以检验题项同质性 |
| 8 题测 3 个因子（3+3+2） | **可行，边界偏紧** | 3 题与 2 题因子的 α 会偏低（Cronbach's α 对题项数敏感）。2 题因子（C）的 α 可能达不到 0.70 门槛。**建议 C 因子优先补到 3 题**（见下方备选） |
| 200 样本够不够 | **够跑 EFA，勉强够跑 CFA** | 量表开发文献建议 EFA 样本 200-300（Guadagnoli & Velicer, 1988；**已核实**），题项与样本比 5:1~10:1。本项目 8 题 200 样本 = 25:1，**EFA 完全够**；若要做 CFA/SEM，200 是下限，建议目标提到 **250-300** |
| 能否得出"这个软件真的会被替代" | **不能** | 这是预测效度，需要纵向数据。见 R6 |

**建议一（优先）：把 C 因子补到 3 题，总数变 9 题。**
备选 C3：「如果这个软件明天涨价十倍，我大概率还是会继续用。」——测的是**支付意愿刚性**，是"锁定"最直接的行为化表达，比 C1/C2 的态度题更接近真实行为，且理论上与转换成本文献直接对接。

**建议二：总分不是终点，效度校验才是。**
8 题能得出的最强结论不是"XX 软件高危"，而是：
- **构念效度**：EFA 是否能抽出预设的 3 个因子（若抽不出，说明维度划分错了，这本身就是 RtD 的发现）
- **聚合/区分效度**：A 因子得分是否与 S2/S3（使用年限、频次）正相关；C2 是否在"被动使用者"（S4）身上系统性偏高
- **个体内比较**：同一 session 连测多个软件时，**个体偏差被消除**，这是本项目数据结构上最大的优势——200 人 × 人均 3 个软件 = 600 条记录，但个体内比较的统计效力远高于 600 条独立样本

**建议三（最重要）：加一个低成本纵向入口，把横断面研究升级为纵向研究。**
结果页放一个**可选**的"留个邮箱 / 微信，6 个月后我回来告诉你，你当时测的这些软件你还在用吗"。
预期转化率 5-15%（200 人 → 10-30 人）。但**这 10-30 人的纵向数据，是整篇论文里唯一能验证预测效度的证据**，也是评审最难挑刺的一节。成本：一个输入框 + 一条定时任务。投入产出比全场最高。

### 关于 F10 的明确反对意见

F10 看似 Reach 高（8），但：
1. **与本项目的核心主张直接冲突**。本项目卖点是"结果可解释、每个维度有方法论出处"；一个 LLM 生成的行动建议恰恰是**不可解释**的。用一个黑箱去解释一个宣称可解释的量表，是自毁立场。
2. Confidence 只有 50%——无法预判 LLM 建议的质量与一致性，且会引入新的效度威胁。
3. **替代方案**：给每个档位配**静态的、由洪兄手写的、逐维度对应的行动建议模板**（高危区 → 重点看 A2 可迁移性，先把能带走的带走）。成本更低、可解释、且与研究主张一致。已并入 F1。

### MVP 范围界定

- **核心 MVP（用户价值层）**：F1 + F2 + F3 + F5。这四项构成完整闭环：能测、能懂、能分享、能反驳。
- **研究必要层（学位作品护身符）**：F4 + F6。成本各约 1-2 人日，但没有它们，这个作品在导师面前就只是"一个趣味测试"。**强烈建议同期做**。
- **Backlog**：F7 / F8 / F9。等 200 样本到手、论文框架定稿后再评估。

## 八、验收标准（Given / When / Then）

**F1 自测流程**
- Given 用户首次访问首页，When 页面加载完成（3G 网络模拟），Then 首屏在 3 秒内可交互，且首屏即展示一个可直接点击的软件示例（不是空白输入框）
- Given 用户选择/输入了一个软件，When 进入答题，Then 8 题全部为 5 点 Likert，单题平均作答时间 ≤ 4 秒，8 题总时长中位数 ≤ 45 秒
- Given 用户答完全部 8 题，When 提交，Then 结果页同时展示：总分、档位、三个因子的分组得分、以及**至少 1 条"拉低你分数最严重的题"及其解释文字**
- Given 用户在结果页点击任意一道题，When 展开，Then 显示该题测的是什么、对应哪条理论（F4）

**F3 分享**
- Given 用户完成测试，When 点击分享按钮，Then 生成一张独立可截图的卡片，卡片上的主文案为第一人称断言句，且不含"欢迎使用"类空洞文案
- Given 用户在结果页，When 点击"再测一个"，Then 不清空 session，新记录与旧记录通过同一 session_id 关联

**F5 反驳入口**
- Given 用户看到结果，When 点击"这个结果不准"并提交文本，Then 该文本与当前记录的 session_id、总分、档位一并入库，且在后台 CSV 中可单独筛出

**F2 数据采集与合规**
- Given 用户完成一次自测，When 数据写入后端，Then 落库字段**不包含** IP 地址、**不包含**精确 User-Agent 原文、**不包含**任何身份标识字段
- Given 用户首次进入答题页，When 第一题渲染，Then 页面中**已展示**知情同意说明（研究目的、匿名性、数据用途、可随时关闭页面中止），这是学术伦理要求，不可省略
- Given 任意时刻，When 运营方导出数据，Then 导出格式为 CSV，一行 = 一次自测，含逐题原始分（未反转前的值与反转后的值**都要存**，便于后续复核）

**F6 回访**
- Given 用户提交回访联系方式，When 入库，Then 该联系方式与答题数据**分表存储**，仅通过随机 token 关联，答题数据表中不含任何可直接联系到个人的字段

**边界与异常**
- Given 用户中途关闭页面，When 重新访问，Then 不恢复未完成的作答（匿名设计，不做草稿），但系统记录 abandon 发生在第几题，用于问卷设计诊断
- Given 用户在 8 题中全部选同一个选项（直线作答），When 提交，Then 结果正常返回（不打断用户体验），但在数据表中该条记录被标记 `straightlining_flag = true`，供分析阶段剔除
- Given 数据写入失败（网络/后端异常），When 提交结果，Then **前端仍完整展示计算结果**（结果计算在前端完成），埋点异步重试，失败不阻塞

## 九、边界条件

| 类别 | 场景 | 处置 |
|---|---|---|
| 空状态 | 用户想测的软件不在预设列表 | 允许自由输入；输入后提示选择一个大致类别（设计 / 视频 / 3D / 文档 / 代码 / 表格 / 笔记 / 音频 / 其他），类别作为分析分层变量 |
| 空状态 | 用户从未用过任何专业软件 | 不设此分支。目标用户定义已排除（见第二节） |
| 错误状态 | 软件名输入为空或仅空白字符 | 阻塞提交，就地提示，不弹窗 |
| 错误状态 | 数据落库失败 | 见验收标准，前端照常出结果 |
| 加载状态 | 结果计算 | 结果在本地即可算出（纯算术），**不做 loading 动画**，直接渲染。若必须做过渡，时长 ≤ 150ms |
| 边界值 | 用户同一 session 连测 15 个软件 | 允许，不限制。这恰恰是最有价值的数据（个体内比较），但后台需防刷：单 session 超过 20 次或单 IP 段异常高频时，标记为可疑数据 |
| 边界值 | 用户在 Likert 上全选"说不清"(3) | 正常出结果。中间分占比过高本身是一个数据发现，论文里应报告 |
| 并发 | 结果页发布后短时间涌入 | 静态资源走 CDN，答题页纯前端计算，后端只承受异步埋点写入，天然抗压 |
| 离线 | 断网状态下打开 | 已加载的页面仍可完成答题并出结果（本地计算）；埋点写入队列暂存，恢复后重试；离线期间明确显示"结果已出，数据待同步"，**不静默失败** |
| 权限 | 用户拒绝/忽略知情同意 | 同意不设强制勾选（会显著降低完成率），但说明文字必须在答题区上方常驻可见。这是"告知—继续即视为同意"模式，**需提前与澳门科大伦理审查口径确认** |

| 异常 | `error_occurred` | `error_type`（api / render / validation）、`message`（脱敏） |

### 11.2 研究数据字段（每次自测一行，导出 CSV）

`record_id` · `session_id` · `timestamp` · `software_name` · `software_category` · `A1..A3,B1..B3,C1..C2 原始分` · `同上的反转分` · `factor_A_score` · `factor_B_score` · `factor_C_score` · `total_score` · `band` · `S1 学习成本形态` · `S2 使用年限` · `S3 使用频次` · `S4 自选/被动` · `duration_ms` · `device_type` · `source` · `straightlining_flag` · `feedback_text` · `sequence_index`

### 11.3 埋点实现要求

- 前端封装统一 `trackEvent(event, props)`，默认附带 `session_id`、`timestamp`、`device`、`version`
- 事件命名规范：`{对象}_{动作}`
- **不采集**：IP 地址、精确 User-Agent 原文、任何可识别到个人的信息、自由文本的软件备注内容
- `session_id` 仅用于"同一人连测多个软件"的关联与个体内比较，**不做跨会话追踪**，建议仅存内存 + 短期本地存储，且提供"清除"入口
- 埋点失败静默重试，最多 3 次，不阻塞主流程

## 十三、给架构师与设计师的关键约束（简版）

**架构师**：
1. 答题与结果计算**必须在前端完成**，后端只承担异步埋点写入与 CSV 导出——这同时满足性能、离线可用与抗压三个需求
2. 联系方式表与答题数据表**物理分表**，仅 token 关联（隐私红线）
3. 数据库字段需支持"原始分 + 反转分"双份存储，导出 CSV 时逐题原始值不可丢
4. 预留 `straightlining_flag` 与 `sequence_index` 字段（这两个是数据分析阶段的关键变量，事后补不回来）

**设计师**：
1. 首屏就不能是空输入框——要有一个可直接点选的软件示例
2. 结果页的**核心是"哪道题拉低了你"**，不是总分数字
3. 分享卡片必须可独立截图，主文案为第一人称断言句
4. 结果计算是本地算术，**不要做 loading 动画**（做了就是在演）
5. 图标为统一 SVG 图标库，不使用 emoji 作功能图标；不使用紫色至粉色渐变主视觉；不使用"欢迎使用""开启你的 XX 之旅"类空洞文案
