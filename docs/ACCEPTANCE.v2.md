## 三、真冲突清单（按严重度）

### 🔴 红：阻塞 Phase 2 开工，必须先裁决

**R1 — 新表名分裂**
- PRD.v2 §1.1 = `followup_results`
- ARCH.v2 §二 = `follow_up_results`
- 后果：两张表在不同文档里各写各的，实施时必然出现迁移脚本与查询代码对不上
- 裁决建议：**采用 `followup_results`**（与既有 `followups` 表前缀一致，下划线更少，PRD 是需求源头）

**R2 — 常模对比阈值相差约 20 倍**
- `SPEC.md:53`（v1.0 基线）明确：同软件常模对比需 **N≥150** 且分软件分层，MVP 样本不支持
- `PRD.v2 §2.2` 却以 **n<8** 为护栏就纳入 P1
- 后果：同一个功能两套准入门槛，测试时无法判定"到底够不够格开这个视图"
- 裁决建议：**两道门槛并存，但语义要分清**——n<8 是"措辞抑制"护栏（不准叫常模），N≥150 是"统计可推断"门槛（才准出分位数）。须在 SPEC.v2 显式覆盖 v1.0 的 §53

**R3 — UIUX §4.2 先验档位方向画反**
- 源码 `domain/bands.ts:16` `PRIOR_CUTPOINTS = [21, 32]`，注释明确：**高危 9-21 / 观察 22-32 / 安全 33-45**
- UIUX.v2 §4.2 画成：**安全 0-21 / 观察 22-32 / 高危 33-45**
- 后果：**看板会把最危险的用户显示成最安全的**，且量程写成 0-100 而实际是 9-45。这是会让研究结论整体反向的错误，不是排版问题
- 裁决建议：以 `bands.ts` 为准重画，并把量程标注统一到 9-45
