## 1. 方向一：纵向回访闭环（F6 / R6 收口）

### 1.1 调研结论

**现状**：`POST /api/v1/followups` 仅登记联系方式入物理分表，`submissions.followup_token` 已可空写入。无定时触发、无发送、无结果录入、无纵向分析视图——即"端点就绪，闭环未合"。

**定时任务技术选型（联网调研 node-cron / node-schedule / BullMQ / 外部 cron）**
- 本工具为单进程 Node + SQLite 部署（香港/新加坡轻量），回访是**低频每日 sweep + 小批量（10–30 条）**作业。
- `node-cron` / `node-schedule`：进程内调度，重启丢失、无重试、无多实例去重——对本场景"每日 sweep"足够（天然可次日补跑），但需**幂等**保障。
- `BullMQ`（Redis）：持久化、重试、去重——对本项目属过度工程，引入 Redis 违背"极薄服务"原则。
- 外部 cron / K8s CronJob：增加基础设施，与当前 Docker 单容器部署不匹配。
- **结论（推荐）**：采用 `node-cron` 每日一次 sweep（`0 9 * * *`，UTC+8 显式时区），对到期 token 发送邮件；发送前写 `followup_sent_at`，**以该标记保证幂等（同 token 只发一次）**。提供 admin 手动触发 + dry-run 端点便于测试。拒绝引入 Redis / 外部调度器。

**联系渠道合规与可行性（调研 邮件 SMTP / 微信模板消息 / Telegram Bot）**
- **主选邮件 SMTP**：环境变量配置发信；香港轻量可达；无需手机号、无需微信认证与服务号模板审批；自带退订/撤回链接天然契合个保法"便捷撤回"。
- 微信模板消息：需认证服务号 + 模板审核 + 订阅关系，合规与可达性成本高，且与"匿名采集"基调冲突，弃用。
- Telegram Bot：国内可达性差，非目标用户（中文创意从业者）主渠道，弃用。
- **结论**：邮件为唯一主渠道；发信走事务邮件实践（SPF/DKIM、显式退订），避免被判定为营销邮件。

**个保法合规（中国大陆，匿名采集下"撤回同意""最小留存"如何落地）**
- 关键定性：`followups` 中的联系方式是**可重识别的个人信息**，不享受"匿名化（个保法第 73 条：无法识别且不能复原）"豁免。匿名答题数据（无 IP、无身份）才是研究资产。两者必须分治。
- 要求清单：
  1. **独立二次同意**：回访 opt-in 与匿名问卷 consent 分离，使用独立 `followup_consent_version`；不在匿名同意里夹带联系采集。
  2. **撤回同意（第 15 条）**：回访邮件内含一键撤回链接 → 触发删除 contact 行（置空 `contact_encrypted`），便捷且即时生效；撤回不影响撤回前已完成的回访处理效力。
  3. **最小留存（第 19 条）**：回访目的在 6 个月达成即应 purge；现有 `contact_purge_after`（12 个月）作为硬上限天花板，建议"回访完成后 +1 月"主动清除，不长期留联系方式。
  4. **目的限定**：联系方式仅用于本次回访，不作营销、不转授。
  5. 加密存储（AES-256-GCM + `CONTACT_ENCRYPTION_KEY`）v1.0 已具备。

**回访问卷最小集（设计原则：<2 分钟、零身份、可纵向比对）**
- Q1 你当时测的那个软件，现在还在常用吗？（还在用 / 很少用了 / 完全不用了 / 换成了别的工具）
- Q2（仅当"换了"）换成了哪类工具？（自由文本，可选）
- Q3 回看当初给你的档位（高危/观察/安全），现在看准不准？（准 / 偏高 / 偏低 / 说不清）
- Q4 有什么变化想说？（自由文本，可选）
- 说明：系统**不预先知道具体软件名**（followups 表按设计不含 software_name，仅冗余 band），由用户自述；纵向分析时经 token 一次性 join `submissions` 取回原软件名与得分。

**纵向数据关联模型**
- 新增表 `followup_results`：`followup_token`(PK) / `still_using` / `switched_to`(可选) / `accuracy` / `notes`(可选) / `created_at`。
- 关联路径：研究者导出纵向视图时，在**受控流程**下以 `followup_token` 将 `followup_results` join `submissions`（取 `software_name`、`total_score`、三因子、原 `band`）；**默认研究导出排除 `followup_token` 列**（ADR-010）。
- 分析层（R/Python，非产品功能）：原 `band`/总分 × 自述 `still_using` 列联表 + φ 系数，检验"感知高 SCC 是否预测留存"——这是全论文唯一预测效度证据。

### 1.2 纳入 / 工作量 / 风险

- **纳入决策：P0**。理由：v1.0 已承诺 F6"研究层强烈建议同期做"；它是论文对抗"你的分数准不准"的唯一防线；投入产出比全场最高；前置端点已就绪，仅补闭环。
- **工作量（人日）**：后端 ~4（结果表 + 端点 + 每日 sweep + 撤回删除 + 受控 join 导出）、前端 ~3（结果录入页 / 撤回页 / 邮件模板 / 二次同意分离）、合规与测试 ~2。**合计约 8–9 人日**。
- **关键风险**：
  - 中——合规落地（独立二次同意文案 + 撤回入口 + 最小留存 purge 作业需可演示，供 IRB 审查）。
  - 中——邮件可达性（香港轻量发信需 SPF/DKIM，否则进垃圾箱；建议走轻量事务邮件 API 或自建 SMTP + DKIM）。
  - 低–中——opt-in 转化低导致纵向 N<10；缓解：结果页显眼但非阻塞的 opt-in 入口，文案用第一人称断言（"6 个月后我回来问你还在用吗"）。

## 2. 方向二：实证分析升级

### 2.1 k-means 切点回写（生产侧）

**重要架构对齐**：ARCHITECTURE.md §374 已明确裁定——"k-means 校准则不在后端实现：导出 CSV → 本地 Python/R 跑 k-means → 把切点回写到 calibration 表。这符合'够用就好'，也避免把统计逻辑塞进一个只有 3 个端点的服务里。"
- 因此 v2.0"生产侧回写脚本"应理解为：**提供离线 k-means 回写脚本（Python）+ 运行手册**，写入 `calibration` 表 `method='kmeans'`，**不建议新增后端 k-means 端点**（违背已锁架构与"极薄服务"原则）。
- 消费侧（`calibration.service` 读取 `method='kmeans'` 切点）v1.0 已就绪，仅缺生产侧脚本。
- **纳入：P1**（数据门控 N≥150；脚本开发可随时做，价值在 N 达标后兑现）。
- **工作量：~2 人日**（Python 脚本 + README 运行手册 + 切点合法性校验，含 k=3、与先验/经验切点偏离度报告）。
- **风险：低**。纯离线脚本，不影响线上服务；主注意点是切点突变需在论文"切点校准"节说明。

### 2.2 同软件常模对比

**统计与小样本展示策略**
- 按 `software_name_norm` 聚合 `total_score` 与三因子分，展示描述统计（均值、中位数、n、最小–最大、四分位）+ 用户自身在同类群体中的**百分等级**。
- 小样本护栏：单软件 **N<8** 时**抑制"常模"措辞**，改标"与你同测此软件的其他人（n=5）"并注明"样本不足仅供参考"；**N<30** 不展示任何推断统计（不画分布假设检验）。
- **防误读（核心）**：严格区分两类分析——
  - *群体常模*：跨**不同用户**同软件聚合（需足够 N）。
  - *个人内比较*：同用户多软件（v1.0 已用 `session_id`；如"我的 Notion 比 Figma 安全"）。
  - 个人内比较**永远不得**称为"常模/群体"。看板与结果页必须显式标注当前视图属于哪一类。
- **纳入：P1**（用户侧价值明显——画像 B 同温层围观者连测多软件；但依赖样本分布，小样本需谨慎标注）。
- **工作量：~3 人日**（聚合 + 导出 ~2；若结果页展示用户百分等级 ~1）。
- **风险：低–中**。主风险是小样本下误读；以 n 阈值 + 显式标注缓解。

## 6. 验收标准草案（EARS / Given-When-Then）

**L1 回访闭环**
- AC-V2-01 回访触发：When 系统每日 sweep 运行，对 `created_at + 6 个月 ≤ now` 且 `followup_sent_at` 为空的 followups，系统**必须**发送回访邮件且**仅发送一次**（幂等由 `followup_sent_at` 保证）。
- AC-V2-02 撤回同意：When 用户点击邮件内撤回链接，系统**必须**删除该 contact 行（置空 `contact_encrypted`），且不保留任何可重识别信息；撤回不影响撤回前已完成的回访。
- AC-V2-03 最小留存：When 当前时间超过 `contact_purge_after`，系统**必须**清除该联系方式（定时 purge 或查询时排除），匿名答题数据不受影响。
- AC-V2-04 纵向 join：When 研究者导出纵向视图，系统**必须**仅在受控流程以 `followup_token` join `submissions` 与 `followup_results`，且**默认研究导出排除 `followup_token` 列**。
- AC-V2-05 二次同意：When 用户进入回访 opt-in，系统**必须**展示独立的二次同意说明（目的/保留期限/撤回方式），**不得**与匿名问卷同意混同。

**L2 实证分析**
- AC-V2-06 kmeans 回写：When 研究者运行离线脚本且 N≥150，脚本**必须**将 kmeans(k=3) 切点写入 `calibration`(`method='kmeans'`)；**代码库不得包含后端 kmeans 端点**。
- AC-V2-07 常模标注：While 展示同软件聚合，系统**必须**标注为"与你同测此软件的其他人（n=..）"；If n<8，系统**必须**抑制"常模"措辞并标注样本不足。

**L3 看板**
- AC-V2-08 防误读：While 展示个人内多软件比较，系统**必须**标注"个人内比较"，**不得使用**"常模/群体"措辞。
- AC-V2-09 看板四视图：When 管理员访问看板，系统**必须**展示档位分布 / 三因子相关 / 漏斗与放弃 / 反驳汇总四类视图，全部基于已采集匿名数据。

**全局规则**
- AC-V2-10 图标/视觉：全代码库**必须**通过 emoji 正则扫描（命中 0）；看板主色墨蓝 `#17557F`，**不得**使用紫粉渐变。

|------|-------------|--------------|
| job-risk.com | 仍基于 Tufts / ESCO 3,039 职业；现 3 档（Express/Career Navigator）+ 6 语言；**55% 职业统计权重未变** | 核心缺陷（职业层、用户回答仅 25%）未变 |
| careery.pro | 新增 "AI Resistance Score" 原创研究（30 职业，与 F&O 校验 r=−0.81）；仍职业层 + 人格化维度 | 仍非"软件级"分析单位 |
| Replaceme（2026-02） | 新进入者：粘贴 LinkedIn/简历 + Claude 给职业风险分 | 职业层，且引入 LLM 不一致性 |
| tryjobhunter "AI Displacement Score" | 500+ 职业任务级评分 + BLS 展望 | 职业/任务层，非软件×使用者 |
| Karpathy 342 职业分析（2026-03） | 高曝光 + 就业展望交叉 | 强化职业层范式 |
| Agent Replacement Index（WhatAreTheBest） | 近 1 年无直接更新；相邻品类转向 AI Agent 安全/沙箱（Cloudflare/AWS 2025–2026） | "软件级替代评估"交互自测仍空 |

**结论**：赛道过去 1 年更偏向"职业层 / 任务层"，**"使用者 × 具体软件"交互自测 + 纵向回访**仍是全网唯一空白。我方差异化与护城河增强而非削弱；且无任何竞品做纵向回访 → R6 仍独家。无需因竞品变化调整 v1.0 定位。

## 8. 非功能与合规补充

| 类别 | 要求 | 优先级 |
|------|------|--------|
| 邮件 | 事务邮件实践：SPF/DKIM、显式退订/撤回；香港轻量部署 | P0（L1 依赖） |
| 隐私 | 回访联系方式 = 个人信息，独立同意 + 撤回 + 最小留存；匿名答题数据长期保留（研究资产） | P0（学术伦理红线） |
| 性能 | 每日 sweep 为低频小批量，不阻塞主请求；admin 看板查询走只读聚合 | P1 |
| 图标/视觉 | 守三规则：无 emoji 图标、无紫粉渐变、主色墨蓝 | P0（团队级） |
